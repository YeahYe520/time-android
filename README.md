# time-android

[`time`](https://github.com/YeahYe520/time) 的安卓外壳。

> ⚠️ **这个仓库单独没有任何用处。** 排程逻辑、数据、AI 翻译全在主项目那边，
> 它只是一个连过去的客户端。先去看主项目。

## 它做两件网页做不到的事

**一、把行程写进手机的系统日历。**
每条事务变成一个日历事件，挂一个"提前 10 分钟"的提醒。提醒是**系统日历
自己发的**——App 关着、屏幕黑着照常响，也能同步到你别的设备。

**二、高优先级的事务到点真的响铃。**
不是弹个通知就完事，是出声、循环、响到你按停为止。

## 它长什么样

```
┌─ 手机 ─────────────────────────────────┐
│                                        │
│   MainActivity  ← 全屏 WebView，就是网页 │
│        │                               │
│        ├─ PlanSync ──→ 系统日历         │
│        │   （每轮同步：拉7天→全清→重建） │
│        │                               │
│        └─ RingScheduler ──→ 精确闹钟     │
│                │                       │
│                └→ RingReceiver         │
│                     └→ RingService     │
│                        （前台服务，放音） │
└────────────────┬───────────────────────┘
                 │ HTTP + 口令
                 ↓
        time 的 Flask 服务
```

**没有一行排程逻辑在这个仓库里。** 它只做两件事：把服务器算好的结果搬进
手机的两个原生系统（日历、闹钟），以及显示那个网页。

代码量 2258 行 Java，**零第三方依赖**——连 AndroidX 都没引，纯
`android.app.Activity` + `android.webkit.WebView`。

## 怎么构建

需要 JDK 17、Android SDK（platform 34 + build-tools 34），然后：

```bash
echo 'sdk.dir=/path/to/Android/sdk' > local.properties
./gradlew assembleDebug          # 或者用你自己的 gradle
```

产物在 `app/build/outputs/apk/debug/app-debug.apk`，用 debug 密钥签名，
手机上直接能装。

## 装上去之后

第一次打开会弹设置面板，填三样：

| | |
|---|---|
| 地址 | `http://<你服务器的地址>:8000` |
| 用户名 | 随便填——服务端只认口令 |
| 口令 | 主项目 `.env` 里 `APP_PASSWORD` 那个 |

然后会依次弹两个权限框（日历、通知），按顺序给就行。

## 三个"不报错但不生效"的坑

写这个 App 的过程中，绝大部分时间不是花在"功能怎么写"，而是花在
**"为什么它明明没报错却什么都不做"**。Android 的日历和闹钟 API
有一批这样的陷阱，列几个最典型的——源码里的注释记着更多：

**一、日历的 `SYNC_EVENTS` 默认是 0。**

不显式写 1 的话，provider 认为这本日历"不同步"，于是**连 Instances 行
都不生成**：事件数据明明在库里，但日历上一条都看不到，提醒也不排。
不报错。

**二、`VISIBLE=0` 时提醒永远不响。**

排闹钟的那条 SQL 里有 `WHERE VISIBLE=1`。用户只要在日历 App 里
取消了这本日历的勾选，事件还在、但通知永远不来。也不报错。

**三、提醒的 `METHOD` 必须写 `METHOD_ALERT`。**

写 `METHOD_DEFAULT`（值 0）——**而这恰好是数据库列的默认值**，
看起来最"正常"——提醒行会成功存进去，日历里说不定还显示个小铃铛，
但 AOSP 排程的查询只挑 `METHOD_ALERT`。于是永远不响，不报错。

> 同类还有：`HAS_ALARM` 网上教程都说要写，**其实写了白写**——
> provider 在 insert 和 update 两条路径上都会把它从 ContentValues 里
> remove 掉。真正决定有没有闹钟的是 Reminders 表里有没有行。

## 一个反直觉的结论

做"到点响铃"的时候，很容易想用**不精确**的闹钟保守一点：
"精确闹钟权限那么麻烦，用 `setAndAllowWhileIdle` 算了，大不了晚几分钟"。

**这条路是死的。** AOSP 里非精确闹钟走 `mOptsWithoutFgs` 那条路径，
**根本不带"后台启动前台服务"的豁免**。结果是闹钟到点了、接收器一启动
服务就抛异常——兜住就是静默无声，兜不住就崩进程。

"保守"的选择在这里恰恰是最坏的。必须走精确闹钟。

而精确闹钟权限这套组合，从 Android 8 到最新版**都不需要用户做任何操作**：

| 版本 | 用什么 | 授予方式 |
|---|---|---|
| 8–11 | 不需要权限 | —— |
| 12 / 12L | `SCHEDULE_EXACT_ALARM` | 安装即授予，用户可撤销 |
| 13+ | `USE_EXACT_ALARM` | 保护级别 normal，**安装即授予且撤不掉** |

两个都声明，`SCHEDULE_EXACT_ALARM` 加 `maxSdkVersion="32"`——这样
Android 13+ 就不看它了，正好绕开"Android 14 起声明了它的新装 App
默认被拒"那条。

## 边界

- **只在真机上过了基本场景。** 厂商 ROM（小米/华为等）对自启动和后台
  弹窗的拦截各家不同，官方文档自己都说"无法统一描述"
- 后台同步是 **best-effort**：JobScheduler 的周期是"每周期**最多**跑一次"，
  Doze 期间完全不跑。**可靠性主干是"每次打开 App 同步一次"**
- 每次同步会**清空「日程」日历再重建**。你在手机上手动改过的事件会被覆盖
- 没有测试。安卓侧的验证全靠真机手动跑
